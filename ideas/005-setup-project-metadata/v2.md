# Set Up Your Project Metadata

**Category:** `[metadata]`

## 1. Symptom

"It's not following my project's conventions! Every time it's missing things!"

You're yelling at the agent because it didn't follow your conventions again. Or: you've picked a tool (003/004), you're invested, but you're running it with zero configuration and wondering why results are inconsistent.

## 2. What to Change

You need to configure your agent for your project. In code you put guardrails on your programs — WHY NOT YOUR CODING AGENTS?

Start a new session. Give it a prompt like:

> "Research best practices for configuring this coding agent to work effectively with this project. Identify where the agent lacks context about our conventions, patterns, and workflows. Use sub-agents to research different areas of the project. Build a plan, then implement the changes."

The agent should:
- Research best practices for agent configuration (for whatever tool you're using)
- Move through the project and identify where metadata is lacking
- Find all the places the agent would spend time confused without enough context
- Update AGENTS files throughout the project (with CLAUDE symlinked to AGENTS — AGENTS has the content, CLAUDE is the symlink)
- Embed coding patterns that are actually in use
- Ask you about specific conventions you care about (especially git workflow)

Key: lean away from creating commands, hooks, and advanced features we haven't talked about yet. If it creates commands the user doesn't know how to use, they're a waste. Keep it to the configuration files and rules.

We may be able to make this generic enough that we don't prescribe "CLAUDE.md" — rather have the agent figure out best practices for itself based on whichever tool is being used.

## 3. Reinforcing Patterns

- Root AGENTS/CLAUDE should be 100-150 lines max. Subdirectories get their own files for specific areas.
- If there are coding patterns in use, they need to be detailed. Not "we use React" but "we use React with this component pattern, this state management approach, this test structure."
- Git workflow: have the agent ask you about your git conventions and embed them so it follows them consistently.
- Run the agent on different areas of the codebase — it should discover the project, not just be told about it.

## 4. Why What You Were Doing Wasn't Working

The agent starts every session with no knowledge of your project beyond what it can read. Without metadata files, it has to rediscover your conventions every time — by reading code, guessing patterns, and often guessing wrong. Every inconsistency in its output traces back to missing context.

## 5. Why the Alternative Works Better

Context gets auto-injected when the agent enters relevant areas. It knows your patterns before it starts writing code. Consistency across sessions improves because the knowledge is persistent — it's on disk, not in a conversation that gets cleared.

This is also the first time you're defining expectations for the agent in writing. You may not realize it yet, but you're taking the first step toward spec-driven work.

## Hidden Arc Note

The action here — "tell the agent the problem, let it research and figure out the approach" — is itself a demonstration of the collaborative pattern. The user isn't dictating file contents. They're describing a problem and letting the agent solve it. This is the mode we want them in for everything that follows.

## Brownfield / Convention Conflicts

For projects with old patterns AND new patterns (brownfield): if you only want new conventions followed, that needs to be explicit in the metadata. "We have two component patterns. The old one (X) exists in /legacy. All new code uses pattern Y. Never use pattern X in new code."

This might be its own sub-article or a section within this one — "specific conventions aren't being followed" as a distinct symptom from "no conventions are configured at all."

## Deliverable: The Prompt

We need to build out a solid, tested prompt that accomplishes this first-pass setup. It should:
- Use sub-agents to research different project areas
- Build a plan before implementing
- Ask the user about key conventions
- Create AGENTS files (with CLAUDE symlinks)
- NOT create commands/hooks the user doesn't understand yet
- Be generic enough to work across Claude Code / Codex / etc. if possible

## Open Questions
- How prescriptive on the prompt? Full copy-paste vs. principles?
- Do we mention the AGENTS/CLAUDE symlink convention or let the agent decide?
- Library-specific patterns (e.g., "we use this ORM this way") — how detailed should metadata get?
- Git workflow embedding — is this 005 or its own piece?
