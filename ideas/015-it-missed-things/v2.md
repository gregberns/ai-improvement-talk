# It Built It But Missed a Bunch of Stuff

**Category:** `[workflow]`

## 1. Symptom

The agent says it's done. You check the work. Stuff is missing. Requirements skipped. Edge cases ignored. It implemented 70% and called it complete. Or it's not following the code patterns correctly.

## 2. What to Change

The FIRST step is NOT to read the code and critique it yourself.

The first step is to have a review performed — leverage the AI to do it.

After implementation, before you accept it:

> "Look at what you built. Compare it against the plan we wrote. What's missing? What doesn't match? What did you skip?"

Point the agent at the plan file. Make it do the comparison systematically.

That's it. Simple prompt.

## 3. Reinforcing Patterns

- Implementation isn't done until the agent has self-reviewed against the plan.
- "Always Be Checkin'" — always have agents check the work. Don't just trust "I'm done."
- This step will also catch code pattern violations — things 014's plan might not have caught because they're convention issues, not requirement issues. Worth noting in 014 that some issues get caught here, not there.

## Two Failure Modes After Review

**Mode 1: The change WAS defined in the plan but wasn't implemented.**
This is the primary case for this article. The agent just... forgot. It happens a lot. The plan said to do X, and it didn't. The fix is straightforward: point the agent at the gap and have it complete the work.

**Mode 2: You realize the change was NOT defined in the plan — something SHOULD have been captured but wasn't.**
This is a different problem. Options:
- Loop back to 014 — improve the plan, then implement the missing piece
- OR — this becomes a later article: "your initial instructions aren't detailed enough, how to improve them"
- OR — we address it later: how to handle edge cases you didn't think of, how to iterate on the plan

We should acknowledge mode 2 exists here, point the reader in the right direction, but not try to solve it in this article.

**Mode 3 (no plan at all): They didn't use 014's approach and things were missed.**
Go back to 014. You need a plan to review against. This article assumes you have one.

## 4. Why What You Were Doing Wasn't Working

The agent forgot. It happens. A lot. It's not always a context issue or a process issue. Sometimes the model just doesn't complete everything.

The answer isn't always "shift left" and improve prior steps. Sometimes the answer is: always have other agents check the work. Build the review habit. Trust but verify.

Without a review step, "done" means "I think I'm done." With a review step, "done" means "I checked and it matches the plan."

## 5. Why the Alternative Works Better

A written plan is a checklist the agent can verify against. Self-review catches gaps before you have to find them manually. You're using the AI to check the AI — leveraging its speed to do the verification you'd otherwise do by reading through code line by line.

The review also catches code pattern violations that aren't about requirements at all — wrong naming conventions, incorrect patterns, style issues. These are things even a perfect plan wouldn't prevent but a review will catch.

## Hidden Arc Note

The user is now doing: plan → implement → review against plan. That's the core loop. When we formally introduce the Ralph Loop later, it'll feel like naming something they already do.

"Always Be Checkin'" — this principle carries through the rest of the series. Review agents, spec review, multi-agent validation. It all builds from this simple habit.
