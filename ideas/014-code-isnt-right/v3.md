# The Code Isn't Implemented Correctly

**Category:** `[workflow]` `[mindset]`

## 1. Symptom

"I told it to implement a new filter in the REST API and it didn't do it right. It doesn't follow conventions. It took the wrong approach. I spent the rest of the day cleaning up after it."

## 2. What to Change

The agent isn't handling your instructions well. It may be because of the pattern of interaction you're using with the agent.

We're going to introduce a different interaction model. It may feel odd.

Think of it this way: **A new developer has joined the team. The PM gave you some instructions but they're not great. Your job: write a set of instructions for this new dev — not on WHAT to do — but tell them about WHY the change needs to be made, give some hints about WHERE the change will probably be made — and DON'T tell them exactly what needs to be done.**

That's it. Describe the problem. Provide context about the surrounding area. Hint at where the change lives. Don't dictate the solution.

**The prompt:**

> Here's a change I need to make. Before writing any code: explore the relevant code and ask clarifying questions until you understand the full picture. Write a plan, then we'll dig into the details one section at a time. Once the plan looks good, write a detailed spec with implementation instructions and code examples to a file. Have an agent review the spec and fix any issues. Break the spec into ordered, discrete tasks in a file, have another agent validate them and fix any issues, then ask me before proceeding. Implement one task at a time. If I don't give you the reason for a change, ask if the context would be helpful. Here's what I need:

The user appends their brainstorm after this. The prompt encodes the full workflow — they don't need to know the steps, the agent walks them through it.

## 3. Reinforcing Patterns

- Save the plan the agent produces to a file. You'll need it for review (015).
- If the plan doesn't match your mental model, correct it BEFORE implementation. That's the whole point.
- Start with one feature. See the difference.
- Resist the urge to dictate the solution. You're giving context and constraints, not step-by-step instructions.
- Note: not everything gets caught at the planning stage. Code pattern violations and implementation gaps get caught in the review step (015). That's by design — the plan catches the big stuff, the review catches the rest.

## 4. Why What You Were Doing Wasn't Working — THE KEY MECHANISM

This is about providing important context AROUND what needs to happen — NOT giving explicit instructions on what to do.

**When you give explicit instructions, the model switches into "Get Shit Done" mode.** You've defined what needs to be done, and it's going to do exactly that. Here's the problem: you didn't properly define exactly what needed to be done. You THINK you did — but you didn't specify the dozens of micro-decisions involved. Which patterns to follow, where to put things, how to structure it, what to name things, how to handle edge cases. You left all of that implicit. The model in GSD mode doesn't ask — it just executes with whatever interpretation it lands on.

**What we want instead: the LLM needs to write the instructions for itself.** Instructions that IT will understand — because it wrote them.

To get there, you need to step back and give the model context that puts it into "plan/reason" mode. Not Claude's Plan Mode feature — the actual LLM needs to understand it needs to think through and reason about the problem. When you provide context about WHY something needs to change, and hints about WHERE, but NOT explicit instructions on WHAT to do — the model says to itself: "To solve the problem this user has presented, I need to explore the code, understand patterns, figure out where things are and need to go, and put together implementation instructions."

**THEN and ONLY THEN — with those detailed, LLM-generated instructions — do we actually go and implement.**

The directive style ("do X in file Y") forces GSD mode. The context style ("here's the problem, here's the area, here's why it matters") forces plan/reason mode. Same model. Dramatically different output.

## 5. Why the Alternative Works Better

When the model writes its own implementation plan:
- It's explored the codebase and found the actual patterns
- It's identified the files, functions, and conventions that matter
- It's reasoned through the approach before writing a line of code
- The plan is in language the model understands — because it wrote it
- You can review the plan and catch misalignment before any code exists

You're not writing more — you're writing earlier. And you're writing the RIGHT thing (context) instead of the wrong thing (incomplete instructions).

## Hidden Arc Note

This is the sneaky spec. The user thinks they're solving "the code isn't right." They're learning to:
- Describe intent and context instead of dictating steps
- Let the agent research, reason, and plan
- Review a written plan before implementation
- Save the plan to disk

That's spec-driven development. They just don't have the vocabulary yet. Don't name it.

The "new developer" analogy is powerful — it reframes the agent from "tool I command" to "teammate I brief." This mindset shift carries through the rest of the series.

The GSD mode vs. plan/reason mode distinction might be the single most important concept in the series. It explains WHY the directive pattern fails and WHY context-first works — in terms of how the model actually behaves, not process methodology.

## Key Deliverable

The prompt template is drafted (see section 2). It encodes:
- Explore → clarify → plan (section by section) → spec to file → agent review → tasks to file → agent validate → ask before implementing
- User just appends their brainstorm/context
- Agent walks them through the process naturally
- Puts the model into plan/reason mode, not GSD mode

This is the baby version of the full spec pipeline (see gist: https://gist.github.com/gregberns/b951f08f2b0b1ac01b0433381654de74). As devs get comfortable with this process, they'll evolve it — eventually creating a skill and refining it through use. That refinement exercise connects back to 006.
