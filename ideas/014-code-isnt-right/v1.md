# The Code Isn't Implemented Correctly

**Category:** `[workflow]` `[mindset]`

## 1. Symptom

"I told it to implement a new filter in the REST API and it didn't do it right. It doesn't follow conventions. It took the wrong approach. I spent the rest of the day cleaning up after it."

This is the pain point. The agent produces code that technically works but isn't what you wanted — wrong patterns, wrong approach, missed conventions. You're frustrated because you told it what to do and it didn't deliver.

## 2. What to Change

Stop telling it what to build and then hoping for the best. Instead, before implementation, run through a short process:

1. You brainstorm the basics of what needs to be built (a few sentences, nothing formal)
2. The agent researches the area of the codebase where the change will live
3. You go through each part together — the agent asks questions, you provide context
4. The agent writes a plan describing exactly what will be built and how
5. You review the plan together — does this match what you want?
6. The agent asks before implementing

## 3. Reinforcing Patterns

- The plan should reference specific files, functions, patterns from the research step
- If the plan doesn't match your mental model, that's the time to correct — not after implementation
- Save the plan to a file. This is your reference for reviewing the implementation later.
- Start small: try this on one feature. See the difference.

## 4. Why What You Were Doing Wasn't Working

When you say "implement a REST filter," the agent has to make dozens of decisions you didn't specify: which patterns to follow, where to put things, how to structure it, what to name things, how to handle edge cases. It guesses. Sometimes it guesses right. Often it doesn't.

The agent isn't stupid — it's uninformed. You know what you want, but you haven't communicated it. The gap between your mental model and the agent's interpretation is where all the "bad code" comes from.

## 5. Why the Alternative Works Better

When the agent researches the codebase first, it sees the actual patterns. When you go through the plan together, misalignments surface before any code is written. When the plan is written down, both you and the agent have a shared reference.

You're not writing more — you're writing earlier. The same conversation would have happened AFTER implementation as complaints and rework. Now it happens before, when it's cheap to change direction.

## Hidden Arc Note

This is the sneaky spec. Don't call it a spec. Don't call it a spec-driven workflow. The user thinks they're solving "the code isn't right." They're learning to describe what they want in writing before implementation — which IS spec-driven development.

The plan file they save to disk is literally a spec. They just don't know it yet.
