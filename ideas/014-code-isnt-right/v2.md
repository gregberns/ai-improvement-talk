# The Code Isn't Implemented Correctly

**Category:** `[workflow]` `[mindset]`

## 1. Symptom

"I told it to implement a new filter in the REST API and it didn't do it right. It doesn't follow conventions. It took the wrong approach. I spent the rest of the day cleaning up after it."

## 2. What to Change

The agent isn't handling your instructions well. It may be because of the pattern of interaction you're using with the agent.

We're going to introduce a different interaction model. It may feel odd.

Think of it this way: **A new developer has joined the team. The PM gave you some instructions but they're not great. Your job: write a set of instructions for this new dev — not on WHAT to do — but tell them about WHY the change needs to be made, give some hints about WHERE the change will probably be made — and DON'T tell them exactly what needs to be done.**

That's it. Describe the problem. Provide context. Hint at the area. Don't dictate the solution.

**The prompt:** We provide a short, simple prompt template they can throw in. The agent will walk them through the rest — researching, asking questions, building a plan, then asking before implementing. The user doesn't need to know the workflow. The prompt encodes it.

## 3. Reinforcing Patterns

- Save the plan the agent produces to a file. You'll need it for review (015).
- If the plan doesn't match your mental model, correct it BEFORE implementation. That's the whole point.
- Start with one feature. See the difference.
- Resist the urge to dictate the solution. You're giving context and constraints, not step-by-step instructions.

## 4. Why What You Were Doing Wasn't Working

When you say "implement a REST filter," the agent has to make dozens of decisions you didn't specify: which patterns, where to put things, how to structure it, what to name things, how to handle edge cases. It guesses. Sometimes right. Often wrong.

The agent isn't stupid — it's uninformed. The gap between your mental model and its interpretation is where all the "bad code" comes from.

The directive style ("do X in file Y") forces the agent into a myopic mode — it does exactly what you said and no more. No looking around for patterns, no considering broader context, no using judgment. You turned it into a typist.

## 5. Why the Alternative Works Better

When you describe WHY instead of WHAT, the agent uses judgment. It researches the area. It finds existing patterns. It asks clarifying questions. It builds a plan you can review before any code is written.

You're not writing more — you're writing earlier. The same conversation would have happened AFTER implementation as complaints and rework. Now it happens before, when it's cheap to change direction.

## Hidden Arc Note

This is the sneaky spec. The user thinks they're solving "the code isn't right." They're learning to:
- Describe intent instead of dictating steps
- Let the agent research and plan
- Review a written plan before implementation
- Save the plan to disk

That's spec-driven development. They just don't have the vocabulary yet. Don't name it.

The "new developer" analogy is powerful — it reframes the agent as a teammate who needs context, not a tool that needs commands. This mindset shift carries through the entire rest of the series.

## Key Deliverable

The prompt template. It needs to:
- Be short (several sentences)
- Encode the "research → discuss → plan → review → implement" workflow without the user needing to know those steps
- Let the user just append their problem description / context / hints
- Have the agent walk them through the process naturally
