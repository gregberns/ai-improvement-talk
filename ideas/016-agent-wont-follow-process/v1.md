# The Agent Won't Follow the Process I Told It

**Category:** `[workflow]` `[metadata]`

## 1. Symptom

"I told it earlier this session to always run tests before committing. It said it was done but it hadn't run the tests!"

"My git workflow skips steps. I have to tell it to push every time. It never creates the PR."

"It said it would follow the process but it just... didn't."

You've tried giving it verbal instructions about process. It agrees, then ignores them. Or follows them once, then stops.

## 2. What to Change

Verbal instructions don't persist. They get pushed out of context, deprioritized, or forgotten. You need to embed process into the project metadata — the same files from 005/006.

For git workflow, this means encoding your exact process:
- After implementing changes: stage, commit with conventional message, push, create PR
- Before committing: run tests/lint/compile
- Don't ask me about these steps — just do them

For test/validation workflows:
- Always run [your test command] after implementation
- Always run [your lint command] before committing
- If tests fail, fix and re-run — don't just report the failure

**This is where rules and hooks get introduced** — not as concepts to learn, but as the mechanism that solves this specific pain. "The agent keeps forgetting to run tests? Here's how to make it impossible to forget."

## 3. Reinforcing Patterns

- Start with one process: git workflow is the most universal
- Add test/validation as the second
- Each time you catch the agent skipping a step, encode it. Don't just tell it again — write it down.
- This is the same evolve-metadata practice from 006, but applied to process, not conventions

## 4. Why What You Were Doing Wasn't Working

Instructions in a conversation are ephemeral. The agent processes them in the moment, but as context grows, earlier instructions lose influence. Long conversations are especially bad — the instruction from 30 minutes ago competes with everything that came after.

Writing "always run tests" in a conversation is like writing a sticky note on water.

## 5. Why the Alternative Works Better

Rules and hooks are loaded at the start of every interaction. They don't compete with conversation context. They don't get forgotten. They're the difference between asking someone to remember something and building it into the system.

This is also the moment where the dev starts to see that encoding process is more effective than directing behavior. The same principle applies to everything that follows — encode it, don't just say it.

## Hidden Arc Note

This article introduces rules and hooks — but the dev experiences them as "the thing that fixed my git workflow," not "a feature of Claude Code." The tool serves the need.

More importantly: the dev is now encoding process in writing. They've gone from verbal instructions → AGENTS files (005) → plans (014) → self-review (015) → encoded process (this). Each step makes writing things down feel more natural. When we formally introduce spec-driven development, they've been doing it for articles.
