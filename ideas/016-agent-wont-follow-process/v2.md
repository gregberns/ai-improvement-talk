# The Agent Won't Consistently Follow Process

**Category:** `[workflow]` `[metadata]`

## 1. Symptom

Choose your own adventure:

- "My git workflow skips steps. It commits but doesn't push. It never creates the PR without me asking."
- "It said it was done but it hadn't run the tests! Again!"
- "I need behavior X to happen consistently, but it only works maybe half the time."

You've tried telling it. It agrees. Then it doesn't do it. Or it does it once, then stops.

## 2. What to Change

Have a conversation with your agent after the problem happens:

> "We're seeing this issue consistently. That signals a problem with our agent configuration — AGENTS.md, hooks, commands, etc. Look back on this past conversation. Understand why the action wasn't taken. Think through what about the information that's been provided is lacking, and where it needs to be improved to consistently execute this action in the workflow — then improve it."

That's it. You're not learning about hooks and rules. You're putting on your engineering hat and asking the LLM "how do we solve this." Make THAT the habit.

The agent will figure out the mechanism — maybe it's an AGENTS.md update, maybe it's a hook, maybe it's a rule. The point is you identified a process failure and asked the agent to fix the underlying configuration.

## 3. Reinforcing Patterns

- Every time you catch the agent skipping a step: don't just tell it again. Run the prompt above. Fix the configuration.
- This is the same evolve-metadata practice from 006, but applied to process, not conventions.
- Think of this like engineering: if a system fails intermittently, you don't just restart it. You find the root cause and fix the system.

**VERY IMPORTANT:** If you do not reinforce this behavior now, you WILL have problems downstream. The later articles in this series assume actions are occurring consistently. If you skip this step, underlying process issues will plague your workflows and cause constant frustration as you try to adopt more advanced techniques.

Example: If you say to a fellow dev "My PR is ready to go," but you haven't pushed all your changes — that's a process problem, not an intelligence problem. The person isn't dumb. The process wasn't well defined. Same with the agent. This is a procedural issue. Procedures need to be well defined for agents — rigorously.

## 4. Why What You Were Doing Wasn't Working

Verbal instructions in a conversation are ephemeral. As context grows, earlier instructions lose influence. The instruction from 30 minutes ago competes with everything that came after.

Writing "always run tests" in a conversation is like writing a sticky note on water.

The agent isn't being disobedient. It's operating without persistent process definitions. You wouldn't expect a new hire to remember every verbal instruction from their first week — you'd put it in the onboarding docs.

## 5. Why the Alternative Works Better

When process is embedded in the agent's configuration, it's loaded at the start of every interaction. It doesn't compete with conversation context. It doesn't get forgotten. It doesn't degrade over long sessions.

You're moving from "telling the agent what to do" to "engineering the system the agent operates in." That's what you do as an engineer — you build reliable systems. Your agent configuration IS a system. Treat it like one.

## Hidden Arc Note

The skill being taught: **when something breaks, ask the agent to diagnose and fix its own configuration.** Not "learn about hooks." Not "memorize the rules syntax." The habit is: identify process failure → have the agent analyze why → have the agent fix its own setup.

This is the same collaborative pattern from 014 applied to configuration. Don't dictate the fix. Describe the problem. Let the agent figure out the mechanism.

The dev is now encoding process in writing through multiple channels: AGENTS files (005), plans (014), self-review (015), and now persistent process config (this). Each step makes "write it down, don't just say it" more natural.
