# Execution Mode vs. Reasoning Mode

**Category:** `[mindset]` `[workflow]`

## 1. Symptom

"The agent wrote a brand new regex parser for email validation — but there's already one ten lines up in the same file. It keeps reinventing things that already exist. It takes the fastest path to 'done' instead of the right path."

Or: "I asked it to add a REST endpoint and it just... went. Didn't look around. Didn't check what patterns we use. Just started writing code immediately."

## 2. What to Change

You already learned (014) to describe the problem instead of dictating the solution. That worked. Now understand WHY it worked — because it controls which cognitive mode the agent operates in.

**Agents have two modes. You're accidentally triggering the wrong one.**

**Execution mode:** The agent receives instructions and begins doing. Tool calls. File writes. Code generation. It's procedural — find the fastest path from A to B and walk it. No detours, no investigation, no "let me look around first." It's pathfinding, and it's optimizing for fewest steps to completion.

**Reasoning mode:** The agent receives a problem and begins thinking. It investigates. Reads code it wasn't pointed to. Considers alternatives. Asks itself questions. Builds a mental model of the space before deciding what to do. It's slower to start writing code — and dramatically better when it does.

The problem: **most prompts trigger execution mode by default.** "Go add this endpoint." "Fix the layout." "Write a function that does X." These are commands. Commands trigger execution. The agent hears a command and switches to procedural mode — "just do the thing" — and stays there.

Can you pat your head and rub your stomach at the same time? It's hard. Agents have the same problem — reasoning and executing simultaneously is not what they're built for. When you trigger execution mode, deep thinking doesn't happen. It doesn't have time to investigate what's available. It's on the warpath to complete the task in as few steps as possible.

**The fix: treat it as two distinct phases.**

1. **Reasoning phase:** Load the agent with context. Tell it the problem, the constraints, the surrounding area. Ask it to investigate, explore, plan. Don't give it permission to write code yet.
2. **Execution phase:** Once the plan exists — written by the agent, reviewed by you — NOW switch to execution. The agent has a complete set of self-generated instructions. It can execute procedurally because the reasoning already happened.

This is the mechanism behind 014's advice. "Describe the problem, not the solution" works because it forces the agent into reasoning mode before it ever touches execution mode. The two-phase approach makes this explicit and intentional.

## 3. Reinforcing Patterns

- Notice when you're writing imperative prompts. "Add X." "Fix Y." "Change Z to W." These are execution triggers. Reframe: "We have this problem because of X. The relevant code is around Y. What approach would you take?"
- When the agent starts writing code immediately after your prompt — without reading files, asking questions, or producing a plan — you triggered execution mode. Stop it. Reframe.
- The prompt from 014 already handles this. But now you understand WHY it works: the "explore, ask questions, write a plan" instructions force reasoning mode before execution begins.
- As you get comfortable, you'll develop a feel for which mode the agent is in. Fast tool calls with no investigation = execution. Reading files, asking questions, producing analysis = reasoning.
- Some tasks genuinely ARE pure execution. "Rename this variable everywhere" doesn't need reasoning mode. The skill is knowing which mode the task requires.

## 4. Why What You Were Doing Wasn't Working

When you give the agent a command — "go add this REST endpoint" — it hears a directive and enters execution mode immediately. No surrounding context. No investigation of what's available, what patterns exist, what conventions are followed. It's doing pathfinding: what's the fastest route from "no endpoint" to "endpoint exists"?

That's why it writes a new regex parser when one already exists. It didn't look. It wasn't in a mode where looking was part of the job. It was in a mode where DOING was the job. Finding the existing parser would require investigation — reasoning mode behavior — but you put it in execution mode.

This maps directly to what Anthropic found in their Economic Index research. They classify interaction patterns as either "directive" (hand the agent a command, expect completion) or "iterative/collaborative" (work together, explore, refine). Their finding: experienced users are MORE iterative and LESS directive. They hypothesized the opposite — that power users would delegate more. But the data shows power users keep the agent in reasoning/collaborative mode longer and use directive/execution mode in more targeted bursts.

The experienced devs aren't doing something fundamentally different. They're just spending more time in reasoning mode before switching to execution mode. They front-load the thinking.

You were doing both at once — or rather, you were skipping reasoning entirely. "Go add this endpoint" is 100% execution trigger, 0% reasoning trigger. The agent never had a chance to think.

## 5. Why the Alternative Works Better

When you separate the two modes:

- **Reasoning mode produces understanding.** The agent reads code you didn't point it to. Finds patterns. Discovers existing utilities. Builds a model of the codebase that's grounded in what actually exists — not what you described from memory.
- **Execution mode, fed by reasoning, produces correct code.** The agent is following instructions it wrote for itself after investigating the codebase. Those instructions reference real files, real patterns, real conventions — because the agent found them during reasoning.
- **You can review the reasoning output before execution begins.** The plan is a checkpoint. If the agent misunderstood the problem or missed something, you catch it before any code exists. Fixing a plan is cheap. Fixing implemented code is expensive.
- **The instructions are in the agent's own language.** When the agent writes its own implementation plan, it produces instructions it can follow precisely. Your instructions, no matter how detailed, are always translated through interpretation. The agent's own instructions need no translation.

The two-phase approach doesn't require more total work. It requires the SAME work, resequenced. Instead of: prompt (execution) → fix → fix → fix, you get: prompt (reasoning) → review plan → prompt (execution) → done. The time you spent fixing bad output now goes into reviewing a plan. Except plan review is faster, and the output is right the first time.

## Hidden Arc Note

This article is the "why" behind 014. The reader has been doing the two-phase approach (014's prompt forces it) for a few articles now. They've seen it work. Now they learn the mechanism.

This is important because understanding the mechanism gives them:
- The ability to consciously choose which mode to trigger
- The language to diagnose when output is bad ("I accidentally triggered execution mode")
- The foundation for later articles about orchestration (007) where you're deliberately switching agents between modes

The Anthropic research connection is also planted here. Experienced users aren't just "better at prompting" — they've intuitively learned to separate reasoning from execution. This article gives the reader the conscious version of that intuition.

The "can you pat your head and rub your stomach" analogy is sticky and physical. Use it. People remember body analogies.

Don't over-explain the LLM internals. The reader doesn't need to know about attention mechanisms or token prediction. They need the behavioral model: commands trigger execution, context triggers reasoning. That's sufficient and actionable.
