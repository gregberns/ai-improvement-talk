Theres a body coordination game: Pat your head, and at the same time rub your belly. 

Try it. Put your hand on your head and move it up and down - on and off your head. Stop. Now put your hand on your belly and move it in circles. Stop.

Easy - right? Now do both at the same time.

We can translate this to agents. In "Process: Code Isn't Right", we discussed a Reasoning mode and Execution mode.

For a refresher - lets use the prompt from that article:

> Add a new REST endpoint POST /api/users/invite. Check if the user exists, generate an invitation token, send an email through the notification service, return the status. Use the auth middleware for admin-only access. Add tests.

You are giving the agent a command - "Do this thing". "Rub your belly".

The agent executes: It finds the API folder, starts implementing the code. Regexes the incoming user email. Writes code to go to the database. Finds the nearest example of notification service. And adds an `if user.isAdmin`. Done!

All the logic is in that function. Theres an inline regex, a bunch of `if` statements, `return Error(HTTP400)` for auth, etc, etc. Just trash. None of your existing libraries/modules/functions were used.

**Problem**

You're not giving the model space to thing and plan.

You're telling the agent to "Pat your head (reason), and rub your stomach (execute)".

**Fix**

Slow down. Think about your process - like your actual development process. You're an engineer. Break your process into steps.

When you are given a problem, do you just start making changes? No. In your head, you break down the problem:
* Remember: how you check users, interact with the users repository, use the 'newer' notification service, and set up auth
* Whats the correct execution order
* What are the edge cases that need to be covered
* etc, etc

You get it. Even if its a task you've done 20 times, you still break down the actions in your head, order them, and setup your plan. It might just take a couple seconds. But you do it. Every time.

For complex or new tasks, we may spend hours or days thinking through the problem.

These models need to do the same. They need to think separately from taking action. Or another way to put it: If your process separates their thinking from their doing - you'll find much more success.

## Two Modes

This idea is so powerful, they have complete models dedicated to one mode - "Reasoning Models".

For the big player's models, Anthropic and OpenAI, they bundle the models together. When you make a request your context is pushed into a 'router' - based on your message it will be routed to the most appropriate set of weights to process your request.
(This may not be 100% correct model - but it should be good enough for us here.)

It either gets routed to the Reasoning model or Execution model. It can't do both at the same time.

It can't Rub its belly and Pat its head at the same time.

So its up to you to trigger the correct model - or mode - you want the LLM to invoke.

Example: While writing this article, there were times were I wanted it to just "Change that word to another one", then other times "Help me think through the different ideas I've laid out". There may be two different execution modes in play. At minimum - there are different sets of nodes in the model that are 'lighting up'.

## Triggering Reasoning

When reasoning first came out, in Claude Code when you typed "think", the word would light up, signaling that the model would go into reasoning mode. That 'router' was just using 'think' as a keyword to push to the reasoning model!!

Since then they've refined that - but still - if you say "Think about this problem" it will trigger that behavior. "Do this thing" will not. 

(At least not generally - you might find that a request might go into reasoning. It might even trigger Claudes 'Plan Mode'. But if we deliberately leverage this, we can get much better performance.)
